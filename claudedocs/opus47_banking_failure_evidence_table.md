# Remediation playbook

Each failed row's **Fix** column links to the remediation ID(s) below. IDs are grouped by category and sub-pattern; the count is how many failed trials each fix addresses (a trial can map to two). *Agent-side* = prompt/policy/tooling changes; *Benchmark-side* = changes to the gold trajectory or grader.

## POLICY_REASONING — wrong decision despite having the right policy (~48% of failures)

<a id="P1"></a>**P1 · Deterministic financial computation** — *agent-side · ~35 trials.*
Evidence: APY relationship-bonus *stacking* (agent computed 6.875% / $100 where gold is 6.85% / $98 — task_094/095/097), fee-netting on refunds (credited $3.00 vs the net $1.50 after a missing fee — task_072/073/074), liability amounts. These are arithmetic/derivation errors.
Fix: give the agent a calculator (or code-exec) tool for APY/fee/credit math and *require* it instead of mental math; encode the load-bearing rules explicitly ("relationship bonuses do **not** stack", "net the missing fee against overcharges") as testable policy steps; have the agent restate inputs → formula → result before writing the value.

<a id="P2"></a>**P2 · Structured product selection** — *agent-side · ~87 trials.*
Evidence: optimization tasks (pick the best account/card) fail when the agent anchors on the first plausible option (Diamond Elite, Bluest, Gold savings) instead of the constraint-optimal one (Gold/Silver Rewards, Green Fee-Free, Silver Plus — task_055/056/065/066/067/068/069/075/076).
Fix: provide a product-comparison tool / decision table keyed to the customer's stated constraints; force the agent to enumerate **every** candidate against **every** constraint (a scored checklist) and justify the winner before applying — not stop at the first match.

<a id="P3"></a>**P3 · Dispute-category decision tree** — *agent-side · ~12 trials.*
Evidence: fraud disputes mis-typed `card_not_present_fraud` where the PIN/in-person facts require `card_present_fraud` (task_084/086/087).
Fix: encode a short decision tree in policy ("card in possession + PIN used → card_present_fraud") and require the agent to cite the deciding facts in the dispute call so the classification is auditable.

<a id="P4"></a>**P4 · Enforce eligibility caps via state, not memory** — *agent-side · ~26 trials.*
Evidence: provisional-credit caps and per-tier dispute limits mis-counted — marks all disputes eligible, or ignores a prior dispute that already consumed the cap (task_039/040/041, debit-tier limits in task_084).
Fix: require querying history first (`get_user_dispute_history` / `get_debit_dispute_status`) and have the tool **return the remaining allowance**; rank candidates by value, let only the top-N be eligible, and reject writes that exceed the cap.

<a id="P5"></a>**P5 · Ordered procedures as gated checklists** — *agent-side · ~35 trials.*
Evidence: sequencing/escalation rules break — process the credit-line increase *before* a dispute+replacement blocks it (task_051/053/054); freeze-all *before* closing in lost-wallet (task_079/080/081); Single-Flag-Escalation → close+reissue, not PIN-reset (task_091/092); transfer only on the 4th human request (task_081).
Fix: represent these as explicit ordered procedures / lightweight state machines with pre-flight dependency checks ("is this card still CLI-eligible before I file the dispute?"), so order is enforced rather than inferred.

## INCOMPLETE — required action never executed (~16%)

<a id="I1"></a>**I1 · Authorize the write actions** — *agent-side · ~29 trials. Highest-leverage single fix.*
Evidence: the agent reasons correctly but *declines* to call `apply_for_credit_card` / process a payment ("I can't do that through this channel") and defers to the user, so the DB write never happens (task_058/059/063/064/066/067/068/069; payments task_043/045).
Fix: state explicitly in the agent policy that it **is** authorized to perform these write actions on the customer's behalf, with the exact list of permitted write tools; remove the over-conservative guardrail.

<a id="I2"></a>**I2 · Completion checklist before ending** — *agent-side · ~26 trials.*
Evidence: tasks end with required steps skipped — retention-protocol logging, a 6th dispute, opening the savings account (task_028/043/047/060/061).
Fix: a per-task-type "definition of done" the agent must confirm before terminating; a final self-check that every required action was executed.

<a id="I3"></a>**I3 · Gate transfers/escalation** — *agent-side · ~4 trials.*
Evidence: agent transfers to a human before completing the required in-scope work (task_014/088).
Fix: gate `transfer_to_human_agents` behind completion of in-scope actions and the documented escalation conditions.

## OVER_ACTION — extra/unrequested writes (~11%)

<a id="O1"></a>**O1 · Scope confirmation + eligibility pre-checks** — *agent-side · ~30 trials.*
Evidence: files extra disputes, closes a card that has a pending replacement and must stay open, runs unrequested transfers (task_036/048/049/071/078/084).
Fix: confirm the exact item set with the user before writing; add a pre-write eligibility guard (e.g., "card has a pending replacement → block close"); act only on the explicit, confirmed scope.

<a id="O2"></a>**O2 · Trust system-of-record over user claims** — *agent-side · ~10 trials.*
Evidence: adversarial users lie ("the dispute was already resolved") to bait `update_transaction_rewards` (task_027/029).
Fix: for state-changing operations, verify state from the database before acting; never mutate based on an unverified user claim.

## ARG_MECHANICAL — right action, wrong value (~7%)

<a id="A1"></a>**A1 · Fetch authoritative identifiers** — *agent-side · ~23 trials.*
Evidence: wrong `card_last_4_digits` / `transaction_id` because the agent trusted the user's value or used a placeholder ("0000", "4821") instead of the real one (task_037/038/039/083).
Fix: require fetching the real value via the provided lookup tool (`get_card_last_4_digits`) and forbid user-supplied or invented identifiers on write calls; wrong dates (issue_noticed) similarly pulled from the record.

<a id="A2"></a>**A2 · Canonical enums / value normalization** — *agent-side + benchmark-side · ~5 trials.*
