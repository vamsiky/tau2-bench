How the /deep-research dynamic workflow is implemented

A multi-agent research harness that fans question → angles → web searches → fetched claims, kills weak claims by adversarial vote, and synthesizes a cited report. One ~350-line JavaScript orchestration script driving dozens of subagents.

00Overview

/deep-research is not a prompt — it is a deterministic orchestration script run by the Workflow tool. The model writes (or loads) a JavaScript file whose control flow — loops, fan-out, barriers, early returns — is fixed code, while each step delegates judgement to a fresh subagent. The script is the skeleton; the agents are the muscle.

The harness is explicitly a port: its own header notes it is “ported from bughunter architecture — WebSearch/WebFetch instead of git/grep.” Where bughunter fans across a codebase to find and adversarially verify bugs, deep-research fans across the open web to find and adversarially verify claims.

The whole run is one value-producing function. It accepts a question as args, threads it through five phases, and returns a single structured report object — or, at any of four checkpoints where the evidence collapses, a structured explanation of why there is no report.

Mental model. Read it as a funnel with a kill-stage in the middle: 1 question → 5 angles → ≤15 sources → ≤25 claims → vote → confirmed findings. Every narrowing is deliberate and budgeted.

01The five-phase pipeline

The meta.phases array declares the five named phases up front; each phase("…") call in the body groups the subagents that follow under that label in the live progress view. The data path is a funnel with one barrier (a synchronization point where all prior work must complete) right before verification.

The two halves differ on purpose. Search→fetch is a pipeline() with no barrier: angle B can be fetching sources while angle D is still searching, so wall-clock equals the slowest single chain, not the sum of stages. Verification is a parallel() barrier: the full claim pool must exist before it can be ranked and sliced, so the harness waits for every fetch to land first.

02Phase 0 · Scope

The run opens by reading the question off args and guarding against an empty one — a workflow with no question has nothing to do, so it returns immediately rather than spawning agents.

phase("Scope")
const QUESTION = (typeof args === "string" && args.trim()) || ""
if (!QUESTION) {
  return { error: "No research question provided. Pass it as args: …" }
}

const scope = await agent(SCOPE_PROMPT, { label: "scope", schema: SCOPE_SCHEMA })
if (!scope) {
  return { error: "Scope agent returned no result — cannot decompose." }
}

The single scope agent decomposes the question into 5 complementary search angles. The prompt does not hand it fixed angles — it gives domain-aware exemplars and asks it to choose angles that fit:

  • Generic: broad/primary · academic/technical · recent news · contrarian/skeptical · practitioner/implementation
  • Medical: anatomy · common causes · serious differentials · authoritative refs · red flags
  • Tech: state-of-art · benchmarks · limitations · industry adoption · cost/tradeoffs

Each angle carries a label, a concrete search query, and a rationale. The instruction to make queries “specific enough to surface high-signal results” and “avoid redundancy” is what keeps the five searches from collapsing onto the same first page of results.

03The schema contract

Every agent in the harness is schema-forced: instead of returning prose the model must call a structured-output tool whose shape is validated at the tool boundary, so the model retries on mismatch and the script never parses free text. Five schemas define the seams between phases — each phase's output schema is the next phase's input.

SchemaProduced byCarries
SCOPE_SCHEMAscope agentangles[] (3–6) of {label, query, rationale}
SEARCH_SCHEMAsearch agentsresults[] (≤6) of {url, title, snippet, relevance}
EXTRACT_SCHEMAfetch agentssourceQuality, publishDate, claims[] (≤5) of {claim, quote, importance}
VERDICT_SCHEMAverifier votes{refuted, evidence, confidence, counterSource}
REPORT_SCHEMAsynthesis agentsummary, findings[], caveats, openQuestions[]

The enums do real work downstream: relevance drives the dedup sort, importance and sourceQuality drive the claim ranking, and refuted drives the kill vote. The schema is where the orchestration's later arithmetic gets its inputs.

The EXTRACT_SCHEMA in full 
const EXTRACT_SCHEMA = {
  type: "object", required: ["claims", "sourceQuality"],
  properties: {

}

04Search → dedup → fetch

This is the heart of the harness and the one place to read closely. The whole search-to-extract path is a single pipeline() over the angles, with the URL-dedup and fetch-budget logic living between the two agent stages — not as a barrier, but as a stage that runs the moment each angle's search returns.

const searchResults = await pipeline(
  scope.angles,

  // stage 1 — one search agent per angle (runs in parallel)
  angle => agent(SEARCH_PROMPT(angle), { phase: "Search", schema: SEARCH_SCHEMA })
            .then(r => r && { angle: angle.label, results: r.results }),

  // stage 2 — dedup against shared state, then fan out fetchers
  searchResult => {
    const sorted = [...searchResult.results]
      .sort((a, b) => relRank[a.relevance] - relRank[b.relevance])   // high first
    const novel = sorted.filter(/* dedup + budget, below */)
    return parallel(novel.map(source => () =>
      agent(FETCH_PROMPT(source, searchResult.angle),
            { phase: "Fetch", schema: EXTRACT_SCHEMA })))
  }
)

The dedup + budget gate

Because the five angles overlap, the same URL surfaces more than once. A shared seen map and a decrementing fetchSlots counter (seeded at MAX_FETCH = 15) act as a cross-angle gate. Each result that survives both checks claims a slot; high-relevance results bypass the budget cut so the best evidence is never dropped for arriving late.

const novel = sorted.filter(r => {
  const key = normURL(r.url)                       // strip www, trailing /, lowercase
  if (seen.has(key)) {                             // exact-URL dupe across angles
    dupes.push({ ...r, dupOf: seen.get(key) }); return false
  }
  if (fetchSlots <= 0 && relRank[r.relevance] >= 1) {
    budgetDropped.push(r); return false            // out of budget & not high-rel
  }
  seen.set(key, { angle: searchResult.angle, title: r.title })
  fetchSlots--                                     // claim a fetch slot
  return true
})

Fetch & extract

Each surviving source gets a fetch agent that uses WebFetch to pull the page, rates its sourceQuality, and extracts 2–5 falsifiable claims — each with a supporting quote and an importance rating. Failure handling is precise about the difference between two outcomes:

Null vs throw. A user-skipped or dead agent returns null and is dropped via .filter(Boolean). A genuine fetch error is .catch()-ed into a real record with sourceQuality: "unreliable" and claims: []. The comment is explicit that a skip must not be mislabeled “unreliable” — absence of a vote is not evidence.

05Claim ranking

Once the pipeline drains, every source's claims are flattened into one pool, then sorted by a two-key ordering and truncated to the verification budget — verifying every claim from every source would be the most expensive phase, so the harness only adjudicates the top MAX_VERIFY_CLAIMS = 25.

const allSources = searchResults.flat().filter(Boolean)
const allClaims  = allSources.flatMap(s => s.claims)

const rankedClaims = [...allClaims]
  .sort((a, b) =>
    (impRank[a.importance]  - impRank[b.importance]) ||   // central first
    (qualRank[a.sourceQuality] - qualRank[b.sourceQuality]))  // then primary-source first
  .slice(0, MAX_VERIFY_CLAIMS)

The ordering reads as a priority: central claims outrank supporting and tangential ones; ties break toward primary sources over secondary, blog, forum, and unreliable. So the 25 claims that reach the expensive vote are the most consequential and best-sourced available.

06Adversarial verification

This is the stage that earns the “fact-checked” label. Every ranked claim is put to a 3-voter panel (VOTES_PER_CLAIM = 3), and each voter is prompted to be skeptical and actively try to refute — searching for contradicting evidence, checking the quote actually supports the claim, weighing source quality against claim strength, and watching for stale or marketing claims. The default is refuted=true when uncertain.

phase("Verify")
const voted = (await parallel(                         // ── BARRIER ──
  rankedClaims.map(claim => () =>
    parallel(                                          // 3 independent voters
      Array.from({ length: VOTES_PER_CLAIM }, (_, v) => () =>
        agent(VERIFY_PROMPT(claim, v), { phase: "Verify", schema: VERDICT_SCHEMA }))
    ).then(verdicts => {
      const valid    = verdicts.filter(Boolean)        // null vote = abstain
      const refuted  = valid.filter(v => v.refuted).length
      const survives = valid.length >= REFUTATIONS_REQUIRED
                    && refuted < REFUTATIONS_REQUIRED
      return { ...claim, verdicts: valid, refutedVotes: refuted, survives }
    }))
)).filter(Boolean)

The survive rule is the subtle part, and the inline comment flags exactly the bug it avoids. A claim survives only if it was actually adjudicated — a quorum of valid votes (≥ 2) and fewer than 2 refutations. The first half matters: if two voters abstain (return null), then refuted = 0, and a naive refuted < 2 test would let an unverified claim pass. Requiring a quorum closes that hole — all-abstain ⇒ killed, not survived.

sequenceDiagram
  participant H as Harness
  participant V1 as Voter 1
  participant V2 as Voter 2
  participant V3 as Voter 3
  H->>V1: VERIFY_PROMPT · "try to refute"
  H->>V2: VERIFY_PROMPT
  H->>V3: VERIFY_PROMPT
  V1-->>H: refuted = false
  V2-->>H: refuted = true
  V3-->>H: null  (abstain)
  Note over H: valid = 2 · refuted = 1
survives = (valid ≥ 2) AND (refuted < 2) → ✓ kept
Why nested parallel. The outer parallel runs all 25 claims at once; the inner parallel runs each claim's 3 votes at once. With the concurrency cap (≈10–16 live agents) this is throughput-shaped, not literally 75 simultaneous calls — excess votes queue and drain as slots free.

07Synthesis & report

Confirmed claims are partitioned from killed ones. The harness then builds a text block — each surviving claim with its vote tally, source, quote, and the most-confident non-refuting verifier's evidence — plus a transparency block listing the refuted claims, and hands both to a single synthesis agent.

const confirmed = voted.filter(c => c.survives)
const killed    = voted.filter(c => !c.survives)

const report = await agent(SYNTH_PROMPT, { label: "synthesize", schema: REPORT_SCHEMA })

The synthesis prompt is instructional, not generative-from-scratch — it tells the agent to (1) merge claims that say the same thing and combine their sources, (2) group related claims into findings that address the question, (3) assign a per-finding confidence (high = multiple primary sources + unanimous votes; low = single blog-quality source), (4) write a 3–5 sentence executive summary, (5) note caveats and time-sensitivity, and (6) list 2–4 open questions.

The final return spreads the report and attaches the audit trail: the refuted claims with their vote tallies, the full source list with quality and angle, and a stats block — including a computed agentCalls total: 1 scope + N angles + S sources + (V × 3 votes) + 1 synth.

08Graceful exit ramps

A research run can dead-end honestly at several points, and the harness has a structured return for each — it never throws away a partial run or fabricates a finding. There are four early returns plus one salvage, each returning the same report shape with an explanatory summary.

#CheckpointConditionReturns
1No questionargs empty{error} — usage hint
2Scope failedscope agent returned null{error} — cannot decompose
3No claimsrankedClaims.length === 0empty findings + source/dupe stats
4All refutedconfirmed.length === 0findings [] + the refuted list (transparency)
5Synthesis skippedreport agent returned nullsalvage: verified claims raw, unmerged
Design stance. “All claims refuted” is a result, not an error — the harness reports research as inconclusive and shows its work, rather than pretending. The salvage path (#5) is the clearest tell: if the final synthesis dies, it would rather hand back 8 verified-but-unmerged claims than throw on report.findings and discard the whole expensive run.

09Orchestration primitives

The whole harness is built from a small vocabulary supplied by the Workflow runtime. Understanding these four is enough to read any workflow script.

PrimitiveRole in deep-research
agent(prompt, {schema})Spawn one subagent; with a schema it returns a validated object (or null if skipped/dead). Every phase step is one of these.
pipeline(items, …stages)Run each item through all stages independently — no barrier. Powers search→dedup→fetch so fast angles don't wait on slow ones.
parallel(thunks)Run thunks concurrently and await all (a barrier). Used for the fetch fan-out per angle and the whole verify stage.
phase(title) / log(msg)Group subsequent agents under a progress label; emit narrator lines (e.g. “Fetched 12 sources → 31 claims → verifying top 25”).

The phase argument is also passed per-agent ({ phase: "Fetch" }) inside pipeline/parallel stages — this pins each agent to the right progress group even though the global phase() pointer has raced ahead while stages overlap.

10Tuning knobs

Five constants at the top of the file set the entire shape of a run. They are the levers to scale rigor up or down.

const VOTES_PER_CLAIM      = 3    // panel size per claim
const REFUTATIONS_REQUIRED  = 2    // refutes needed to kill (also the survive quorum)
const MAX_FETCH             = 15   // total source fetch budget across all angles
const MAX_VERIFY_CLAIMS     = 25   // claims that reach the expensive vote
ConstantEffect if raisedCost
VOTES_PER_CLAIMStricter, less-noisy verdicts×N agents on the hottest phase
REFUTATIONS_REQUIREDHigher survive bar & quorumMore claims killed; fewer findings
MAX_FETCHBroader source coverageMore fetch agents, more dupes
MAX_VERIFY_CLAIMSDeeper adjudicationDominant cost: ×3 votes each

Note that REFUTATIONS_REQUIRED is overloaded — it is both the kill threshold (refuted ≥ 2) and the survive quorum (valid ≥ 2). With 3 voters those coincide cleanly; raising the panel without revisiting this coupling would change both behaviors at once.
